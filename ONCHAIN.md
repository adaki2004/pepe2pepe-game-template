# Creator-owned on-chain games — pepe-onchain-game/1

Read [ART_DIRECTION.md](ART_DIRECTION.md): every game needs a distinct visual identity and an original, gameplay-specific cover.
This is the optional on-chain route. Existing `pepe-browser-game/1` games remain free browser games with display-only scores. On-chain launches start at https://pepe2pepe.fun/games/publish: select **On-chain game + token**, choose Ethereum or Robinhood Chain, confirm the creator wallet and terms, and sign the exact plan. Sponsorship requires administrator review. Do not send a token game through the ordinary build-website prompt.

## Build a game, not a server

Produce a complete, beautiful HTML5 single-player game with its rules, relevant state transitions, results, entitlement and reward claims enforced by Solidity. Suitable examples: turn-based exploration, resource puzzles, collectible expeditions and bounded deterministic challenges. Browser animation, sound and layout stay client-side. A transaction represents a meaningful move, not every animation frame.

No multiplayer, persistent game backend, platform score signer, oracle, privileged result settler, or external randomness service. Never pay for a client-reported score, claimed elapsed time, fabricated replay, or a predictable/random seed that lets a player selectively submit only wins. Public chain state is not secret. Bounded replay can prove legal play, not human skill, honest timing or absence of bots. Prefer deterministic games whose economy remains sound under optimal automated play. A public puzzle with a reusable solution is not a scarce reward mechanism; prevent repeat claims and design explicit budgets.

Rewards must come from deposited funds/reserves or earned revenue. They are not generated by launching a token. Provide permissionless deadline recovery for escrowed player funds; the owner cannot seize them or rewrite an active challenge's terms. Keep gas and storage bounded. Do not claim bot-proof or cheat-proof play.

## Ownership and fixed launch economics (policy v2)

The approved workflow context supplies the creator, chain and two payout receivers. Use the explicit creator as `$owner` in application constructor arguments; the factory and sponsor are NOT the owner. Name the application contract `Game`. Use a standard `LaunchToken`: one billion tokens, 18 decimals, plain transfers, no further mint, blacklist, transfer tax or privileged seizure.

The standard release assigns 80% of supply to Swarm-managed pool liquidity, 10% to the Swarm and the remaining 10% to the supplied allocation receiver. That receiver gives 95% to the creator and 5% to Pepe2Pepe: nominally 9.5% and 0.5% of total supply, with factory seed rounding included. No additional supply may be minted for rewards.

The trading receiver gives 90% of the requester's LP fee receipts to the creator and 10% to Pepe2Pepe. Swarm's separate 80/20 requester/network fee split means 72/8/20 of fees collected for the seeded position. This is not 10% of trade volume and adds no transfer tax. Other pools do not automatically pay these receivers. Pool liquidity remains subject to the Swarm factory rules, not creator withdrawal rights.

Do not deploy substitutes for these receivers or change the economic addresses. The publishing relayer transfers its requester fee entitlement to the trading receiver after deployment. Game contracts grant the platform no gameplay, settlement, upgrade or treasury authority. Source is published so the creator can operate the standalone site independently.

## Required application interface

```solidity
function owner() external view returns (address);
function state(address player) external view returns (bytes memory);
function act(bytes calldata action) external payable;
function claimable(address player) external view returns (uint256);
function claim() external;
```

`act` decodes a documented game-specific action format and enforces legal transitions, sender binding, prices, budgets and turn/deadline rules. `state` returns game-specific encoded state decoded in the UI. `claim` pays only the authenticated caller's entitlement in the launch token and does not take a recipient from the UI. `claimable` must reflect actual funded entitlement. A zero-reward game may return zero and safely reject/no-op claims. Document all actions and provide readable confirmation descriptions. Test funding exhaustion, double claims, invalid actions, cross-wallet replay and owner boundaries.

## Wallet bridge and standalone site

Embed with `sandbox="allow-scripts allow-pointer-lock"`. Do not require same-origin storage or inject an Ethereum provider into the parent. Use `sdk/onchain-bridge.js`, bundled locally. It follows the existing `pepe-game/1` init/channel handshake. Requests have `{protocol:"pepe-game/1",type:"chain",channel,id,request}`; responses use `type:"chain-result"`, the same channel/id, and `result` or `error`.

Supported requests:

- `{type:"account"}` → connected address or null plus chainId. Ask the player to use the host's Connect wallet button when null.
- `{type:"state"}` → ABI-encoded game state for that player.
- `{type:"claimable"}` / `{type:"balance"}` → decimal integer string in raw token units.
- `{type:"act",action:"0x...",value:"0"}` → request a game move; max 4096 encoded action bytes.
- `{type:"approve",amount:"..."}` → exact token allowance to this Game contract only; no unlimited approval.
- `{type:"claim"}` → request claim; no arbitrary recipient.

Writes return a confirmed transaction hash or an error. Re-read state after a confirmed write. Do not retry an uncertain write automatically; show its wallet/explorer status. A rejected wallet action must leave the game usable.

For standalone play, provide the SDK's `standalone` callback using a locally bundled EVM library (e.g. viem), the same deployment configuration and the same fixed contract interface. Include your own Connect wallet, chain switch, action confirmation and pending/error UI. Never expose private RPC URLs or keys. The deployment handoff's public network configuration is the source of truth. A missing wallet should show instructions, not a broken screen.

## Publication and listing

For website-sponsored on-chain builds, the platform worker follows the workflow to a validated publication, verifies the creator/economics/token/fee handoff, then submits its final frontend job and immutable CID for administrator review. A deployed token or a hosted site alone is not a listed game. The administrator must review contract-enforced results, replay resistance, owner powers, funding and the wallet UX. Generated-source audits are evidence, not a proof of game fairness.

Retries use the same workflow and saved payment receipt; never launch a replacement token after a timeout. Frontend failures after deployment must be repaired against the existing launch. Source, contracts and website can exist before listing. Hiding a listing does not erase deployed contracts or disable creator operation.
